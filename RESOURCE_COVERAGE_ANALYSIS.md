# FHIR Resource Type Coverage Analysis

> ### ⚠️ Correction (2026-08-25): Google FHIR Stages 2 and 3 are NOT stubbed
>
> This document repeats a claim that is false. Verified by running the harness:
>
> | | Claimed | Actual |
> |---|---|---|
> | Stage 2 (materialize) | "returns 0 ns" | **implemented** — parses the TLV records, `ParseFromArray` per message, protobuf-reflection walk. 9,539 nodes touched, ~1.6 ms on a 1 MB bundle. |
> | Stage 3 (query) | "returns 0 ns" | **implemented** — 42 accumulator calls. Returns `patients=1 observations=316 obs_issued_present=316`, matching the JSON baseline exactly. |
>
> There is no `0`-duration metric push anywhere in `arm_google_fhir.cpp`. The
> ~80 h of Stage 2/3 work this document schedules as P1 appears to have been
> done at some point without the docs being updated.
>
> **Two real Google-arm gaps remain**, and they are not the ones described here:
>
> - `birthdate` is reported as a microsecond epoch (`194140800000000`) where
>   every other arm reports ISO (`1976-02-26`). A normalization gap.
> - The Google arm is **excluded from `validate_parity()`**, which only compares
>   FastFHIR-vs-JSON and JSON-vs-HL7v2. Its query results are therefore never
>   checked against another arm.
>
> See [notes.md](notes.md) and [TASKS.md § PARITY](TASKS.md).

> **Stale denominator — reviewed 2026-08-24.** This analysis was written when
> FastFHIR compiled **28** resource types. At the current profile
> (`us-core,billing,medication-admin,supply`) it compiles **37**, from 44
> generated `.cpp` files. Wherever this document says "28", read "37", and
> wherever it says "2/28 = 7%", read "2/37 = 5%" — **the gap is wider than
> documented, not narrower.**
>
> Two further corrections that change how this analysis should be read:
>
> - **The denominator is profile-dependent, not a property of FastFHIR.** It
>   moves whenever `FASTFHIR_PRODUCTION_PROFILE` changes, and Bazel gives no
>   signal when it does. See [README § Result provenance](README.md#result-provenance).
> - **Uncompiled ≠ unsupported.** Resource types outside the profile are no
>   longer dropped; they are retained as opaque JSON and re-emitted
>   byte-for-byte. They round-trip losslessly but are **not typed-navigable** —
>   no V-Table, so no field access, query, or interior compaction. A coverage
>   number therefore measures *navigable* surface, not *representable* surface.

## Executive Summary

This analysis identifies FHIR resource types across the benchmark harness, FastFHIR installation, and Google FHIR implementation. The benchmark currently tests only **Patient** and **Observation** while both libraries support significantly broader resource coverage.

## 1. Currently Tested Resources (Benchmark Harness)

### Primary Test Resources
The benchmark actively measures serialization (Test 1), deserialization (Test 2), and query performance (Test 3) for:

| Resource | Status | Includes | Notes |
|----------|--------|----------|-------|
| **Patient** | ✅ Active | FF_Patient.hpp | Full FHIR Patient profile; critical query target for birthDate |
| **Observation** | ✅ Active | FF_Observation.hpp | Cholesterol LOINC 2085-9 observations; key query metric |
| **Bundle** | ✅ Active | FF_Bundle.hpp | Collection container; wraps Patient + Observation entries |

### Supporting Resources (Data Structures Only)
These resources are referenced in `harness.hpp` but are **not actively serialized/queried** in the current benchmark:

| Resource | File | Purpose |
|----------|------|---------|
| Encounter | FF_Encounter.hpp | Fixture data structure; available for future expansion |
| Condition | FF_Condition.hpp | Fixture data structure; available for future expansion |
| Procedure | FF_Procedure.hpp | Fixture data structure; available for future expansion |

### Test Scope Details
- **Test 1 (Serialize)**: Converts `BundlePatient` struct → library-specific wire format
  - All arms serialize Patient + Observation entries deterministically
  - Shared assignment flow ensures parity across FastFHIR, JSON, Google FHIR, HL7v2
  
- **Test 2 (Materialize)**: Parses wire format → in-memory DOM
  - FastFHIR: Reflective::Node tree via Parser
  - JSON: simdjson::dom::element tree
  - Google FHIR: Protobuf message objects (stub for Stage 2/3 pending implementation)
  - HL7v2: Custom segment structure

- **Test 3 (Query)**: Extracts target values from DOM
  - `Patient.birthDate` (all arms)
  - `Observation.code.coding[].code == "2085-9"` with `system == "http://loinc.org"`
  - Observation value type variants (Quantity, CodeableConcept, String, Code)

## 4. FHIR Scope & Versioning

### Version Strategy
| Library | Primary | Secondary | Notes |
|---------|---------|-----------|-------|
| **FastFHIR** | R4 | R5 available | Dual-dictionary support; auto-generated headers |
| **Google FHIR** | R4 | Not observed | Protobuf generation for official Google FHIR R4 spec |
| **JSON** | R4 | Flexible | nlohmann/json parses any FHIR JSON; no type coupling |
| **HL7v2** | v2.5 / v2.8 | Indirect | Maps FHIR → HL7v2 segment format; loose coupling |

### Specification Target
- **All arms** currently target **FHIR R4 (Release 4 / STU 4)**
- **No R5 benchmarks** are active (FastFHIR R5 dictionary exists but not exercised)
- **Version locking**: Harness and fixture assume R4; any R5 work would require new test paths

## 8. Key Findings & Recommendations

### Finding 1: FastFHIR is Feature-Complete
- ✅ 28 resources with full FHIR R4 compliance
- ✅ Both R4 and R5 dictionaries available
- ✅ All resources have public + internal header pairs (consistency)

**Recommendation**: Use FastFHIR as ground truth for resource availability reference.

### Finding 2: Google FHIR Coverage Undocumented
- ⚠️ Only Patient/Observation confirmed in benchmark
- ⚠️ Full resource list requires Bazel workspace audit
- ⚠️ Stage 2/3 implementation needed for fair comparison

**Recommendation**: 
1. Run `find .external/google-fhir -name "*.proto" | grep "resources/"` to list all available protos
2. Document which resources are linked into the benchmark
3. Prioritize Stage 2/3 implementation for Patient/Observation before expanding to other resources

### Finding 3: Benchmark Scope Narrow but Defensible
- ✅ Patient + Observation covers 40-60% of typical EHR workflows
- ⚠️ Missing medication, encounter, procedure data reduces real-world realism
- ⚠️ Cholesterol LOINC (2085-9) is narrow; could use multi-code queries

**Recommendation**: 
1. Expand to Encounter + Condition + Procedure (high ROI, 80% coverage)
2. Use multi-code LOINC queries (HDL, LDL, triglycerides in addition to total cholesterol)
3. Consider synthetic Bundle payloads with full nested resources

### Finding 4: Test 2/3 Incomplete for Google FHIR
- ⏳ Stage 1 (Serialize) only implemented
- ⏳ Stage 2 & 3 stubs return 0 ns

**Recommendation**: Prioritize Google FHIR Stage 2 & 3 for fair three-arm comparison (FastFHIR, JSON, Google FHIR all complete) before extending resource coverage.
